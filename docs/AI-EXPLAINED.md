## 1. The one-minute version

> **"The AI provides assistive risk assessment and suggests an appropriate
> medical specialty. It is not a diagnostic system."**

A patient describes their symptoms in the app, in English or Arabic. The AI
answers two questions:

1. **Which department should this patient see?** (cardiology, dermatology, …
   17 specialties)
2. **How urgent is it?** (LOW, MODERATE, HIGH, or CRITICAL)

It never names a disease. Every answer comes with the reasons behind it, is
saved for a doctor to review, and carries a disclaimer.

It is built from three parts:

| Part | What it is | Its job |
|---|---|---|
| **Safety layer** | Hand-written rules (keywords such as "chest pain") | Catch emergencies. Always wins. |
| **Specialty model** | A small model we trained ourselves | Route the patient to a department |
| **Risk model** | A second small model we trained ourselves | Estimate urgency |

There is **no ChatGPT, no paid API, no internet call**. The models are two
files (about 13 MB together) that run on our own server, typically answer in
under a tenth of a second, and can show which words led to each answer.

Headline numbers (details in section 9):

- Specialty routing: **99.6%** correct on held-out test data, against 31.0%
  for the keyword rules the back-end used before.
- Urgency: the full service flags **93.6%** of the truly urgent test cases as
  urgent; the rules alone flag 68.0%.
- Emergencies: of 208 test cases that are truly life-threatening, the rules
  alone catch 175; rules plus model catch **204**, with no false emergency
  raised by the model.

And the two caveats you should state yourself: the test data is largely
synthetic, and on a disease the model has never seen, routing accuracy is
about 50%.

## 2. Where the AI sits in the system

```
 Flutter app                NestJS back-end                    Python ML service
┌───────────┐  POST        ┌──────────────────────┐  POST     ┌──────────────────┐
│  patient  │ ───────────► │ /api/v1/ai/triage    │ ────────► │ /triage          │
│  types    │              │                      │  (JSON)   │  FastAPI         │
│  symptoms │ ◄─────────── │ AiService            │ ◄──────── │  2 models+rules  │
└───────────┘   result     │  ├ builds the input  │           └──────────────────┘
                           │  ├ calls AiProvider  │            127.0.0.1:8000
                           │  └ saves Assessment  │            (never public)
                           └──────────┬───────────┘
                                      │ if the ML service is down or slow (>8 s)
                                      ▼
                           built-in rules engine (TypeScript)
```

The back-end side already existed before the models did. It uses the
**Strategy pattern**: `AiService` depends on an `AiProvider` interface, and a
factory in `ai.module.ts` picks the implementation from configuration.

| `AI_SERVICE_URL` in `.env` | Provider used | `engine` field in the response |
|---|---|---|
| empty | `RulesAiProvider` — keyword rules in TypeScript | `rules` |
| `http://localhost:8000` | `MlHttpAiProvider` — calls the Python service | `ml-service` |
| set, but the service is down / slow / returns garbage | falls back to `RulesAiProvider` | `rules-fallback` |

So switching the AI on is a **configuration change, not a code change**, and
the triage endpoint can never fail because of the AI: the worst case is the
old behaviour.

Three things worth pointing out to a committee:

- **Data minimisation.** NestJS sends only clinical context — age, gender,
  chronic diseases, symptoms, notes. No name, email, phone or id ever reaches
  the ML service.
- **Privacy.** The ML service listens on `127.0.0.1` only. Patient text never
  leaves our server.
- **Human in the loop.** Every triage is stored as an `AI_INITIAL` Assessment,
  so the doctor sees what the AI said and why at the next visit.

### The contract between the two services

```jsonc
// NestJS → Python          POST /triage
{
  "age": 61,
  "gender": "MALE",
  "chronicDiseases": "type 2 diabetes, hypertension",
  "symptoms": [{ "name": "chest pain", "duration": "2 hours", "severity": "severe" }],
  "notes": "pain spreads to my left arm"
}

// Python → NestJS          200 OK
{
  "riskLevel": "CRITICAL",                 // LOW | MODERATE | HIGH | CRITICAL
  "suggestedSpecialty": "cardiology",
  "seekEmergencyCare": true,               // app shows the SOS card
  "redFlags": ["Chest pain"],
  "reasons": ["Red-flag rule matched: Chest pain.", "Symptoms described as severe.",
              "Chronic conditions on record."],
  "advice": "Your symptoms may be serious. Call emergency services (123 in Egypt) or press the SOS button now."
}
```

## 3. What happens to one request

Take this request: a 34-year-old writes *"I have a high fever with chills and
shivering, a bad headache, and my muscles ache all over. I have also been
vomiting since yesterday."*

| Step | What the service does | Result for this request |
|---|---|---|
| 1. Normalise | Lower-case the text; if it is Arabic, translate it word by word with an offline dictionary | already English |
| 2. Red flags | Search for emergency phrases (chest pain, can't breathe, stroke signs, …) | none found → continue |
| 3. Specialty model | Turn the text into numbers, compute a probability for each of the 17 specialties | infectious disease, 0.91 |
| 4. Explain | Look up which words pushed that answer | "headache", "high fever", "chills" |
| 5. Risk model | Build 159 numeric features (recognised symptoms, severity words, age, …) and vote | HIGH, 0.92 |
| 6. Rule floors | Apply fixed minimums: "severe" → at least HIGH; age ≤ 5 or ≥ 65, chronic illness, or 3+ symptoms → at least MODERATE | nothing to raise |
| 7. Respond | Build the JSON with the reasons and the advice text | below |

```json
{
  "riskLevel": "HIGH",
  "suggestedSpecialty": "infectious disease",
  "seekEmergencyCare": false,
  "redFlags": [],
  "reasons": [
    "Model confidence 0.91 for infectious disease (key terms: headache, high fever, chills).",
    "Risk model predicted HIGH (confidence 0.92)."
  ],
  "advice": "Please book an appointment as soon as possible — we suggest the infectious disease department."
}
```

Four more real answers, to show the different paths:

| Input | Answer | Why |
|---|---|---|
| "chest pain", severe, 61 years old, diabetic | CRITICAL · cardiology · SOS | Red-flag rule. The models are not even consulted. |
| "طفح جلدي وحكة" (skin rash and itching) | LOW · dermatology | Translated to "skin rash itching"; short input, so a keyword rule routes it. |
| "headache" | MODERATE · neurology | Short input: keyword rule for the specialty; the risk model may say MODERATE at most. |
| "vomiting", "breathlessness", "sweating" | CRITICAL · cardiology · SOS | No red-flag phrase, but the risk model recognises a heart-attack pattern. |

## 4. The machine-learning ideas you need

If you can explain this section, you can defend the project.

### A model is a function that was learned instead of written

As a back-end developer you write `f(input) → output` by hand. In machine
learning you provide thousands of **examples** of inputs with the correct
outputs, and an algorithm finds the function for you.

- **Training** = running that algorithm once, offline. It produces a file.
- **The model** = that file (`specialty.joblib`, `risk.joblib`). Think of it
  as a compiled artifact.
- **Inference** (or prediction) = loading the file and calling it. This is
  all the server does; it never trains.

Our two models are **classifiers**: the output is one label out of a fixed
list (one of 17 specialties; one of 4 risk levels), plus a probability for
each label. The highest probability is reported as the **confidence**.

### Models only understand numbers: features

A model cannot read text. Each input must become a fixed-length list of
numbers, called **features**. How we do that is most of the design:

- For the specialty model, the text becomes word-importance scores (TF-IDF,
  below).
- For the risk model, we compute 159 numbers by hand: how many known symptoms
  were mentioned, their severity weights, the patient's age, and so on.

### TF-IDF — turning text into numbers

**TF-IDF** (term frequency × inverse document frequency) gives every word in
a text a score:

- high if the word appears in *this* text (term frequency),
- lower if the word appears in *almost every* text (inverse document
  frequency).

"Rash" is rare overall and tells you a lot, so it scores high. "Pain" is
everywhere and tells you little, so it scores low. Filler words ("I", "have",
"the") are removed entirely. We also count pairs of adjacent words
("chest pain", "high fever"), because pairs carry meaning single words do
not.

The result: each text becomes a list of 4,226 numbers, one per known word or
word pair, almost all of them zero.

### Logistic regression — the specialty model

Despite the name, it is a classifier. For each specialty it learns one
**weight per word**. To classify a text it multiplies each word's TF-IDF
score by its weight for that specialty, sums them, and turns the 17 sums into
probabilities.

Why this matters for the defence: **the weights are readable**. After
training, the strongest words per specialty are, for example:

| Specialty | Words with the largest weights |
|---|---|
| dermatology | skin, sores, rash, pimples, nails, blackheads |
| urology | pee, urinate, urine, bladder |
| psychiatry | dying, feeling detached, tingling, surroundings |

Nobody wrote these lists. The model found them in the data, and they make
medical sense. That is what "explainable" means here — and it is why the
service can say *"key terms: headache, high fever, chills"* next to the
model's answer.

### Random forest — the risk model

A **decision tree** is a flowchart of yes/no questions on the features ("is
the total severity weight above 12?" → "is the patient older than 65?" → …)
ending in a risk level. One tree is easy to read but unreliable. A **random
forest** trains 300 different trees, each on a random part of the data, and
lets them **vote**. The share of the vote is the confidence.

It suits the risk model because its inputs are a table of mixed numbers
(counts, ages, flags), which trees handle well without any tuning.

### Never test on the data you trained on

A model can memorise its examples and still fail on new ones (this is called
**overfitting**). So before training we set aside 20% of the data as a **test
set** the model never sees. All reported numbers are measured on that 20%.

A related trap is **data leakage**: when a test example sneaks into training,
the score looks better than it is. One of our datasets has 4,920 rows that
are really 304 distinct rows copied many times; a naive split would put
copies of every test row in the training set and report nearly 100%. We
remove duplicates *before* splitting. This is a detail a good examiner will
appreciate.

### The metrics

| Metric | Plain meaning |
|---|---|
| **Accuracy** | Out of all answers, how many were right. |
| **Recall** (for a class) | Out of the cases that truly are X, how many did we call X. *"Of the urgent patients, how many did we catch?"* |
| **Precision** (for a class) | Out of the cases we called X, how many truly are X. *"When we say urgent, how often is it true?"* |
| **F1** | One number combining precision and recall. |
| **Macro-F1** | F1 averaged over the classes, each class counting equally — so a rare specialty matters as much as a common one. |
| **Confusion matrix** | A table of "true class" against "predicted class"; shows *which* classes get mixed up. The PNG files in `reports/`. |

In medical triage the costly mistake is **missing a sick patient**, so the
number we care about most is recall on the urgent classes. The price of high
recall is **over-triage** — telling some non-urgent patients it is urgent. We
report both.

### A baseline — compared with what?

A number means nothing alone. Our **baseline** is the keyword rules engine
that already existed in the back-end. Every result in section 9 is shown
next to what those rules score on exactly the same test cases. "Rules: 31% —
trained model: 99.6%" is the story of the project in one line.

## 5. The data

All three datasets are public and free.

| Dataset | What it contains | Rows we use |
|---|---|---|
| **Symptom2Disease** (Kaggle) | Symptom descriptions in patients' own words, each labelled with one of 24 diseases | 1,153 |
| **Disease Symptom Prediction** (Kaggle) | Symptom checklists for 41 diseases, plus a severity weight (1–7) for each of 131 symptoms | 304 distinct checklists |
| **DDXPlus** (research dataset, NeurIPS 2022) | 1.3 million *synthetic* patients for 49 conditions, each a list of coded findings with age and sex | 2,474 (60 distinct symptom profiles per condition) |

Together: **3,931 examples, 83 diseases, 17 specialties**. Split 80/20 into
3,145 training rows and 786 test rows, keeping every disease and every dataset
in the same proportion on both sides (a *stratified* split).

### From disease labels to what we predict: the disease table

The datasets label each example with a **disease**. We do not want to predict
diseases — that would be diagnosis. So one table,
`smartcare-ml/data/specialty_map.csv`, converts each disease into the two
things we do predict:

| disease | specialty | acuity |
|---|---|---|
| psoriasis | dermatology | LOW |
| pneumonia | pulmonology | HIGH |
| heart attack | cardiology | CRITICAL |

This table is **the only place where medical knowledge enters the models**,
and it is a deliverable in its own right (put it in the appendix).
`smartcare-ml/data/SPECIALTY_MAP.md` documents how each row was decided:
ICD-10 code for the specialty, written definitions for the four urgency
levels, DDXPlus's own severity ratings for its conditions, and the ten rows
that were changed in review with the NHS / StatPearls reference for each.

Be exact about its status: it was reviewed against references, **not signed
off by a clinician**.

### Three data problems we found and how we handled them

1. **Duplicates** in the checklist dataset (4,920 rows → 304 distinct).
   Removed before splitting, as explained above.
2. **Class imbalance.** Some specialties have ten times more examples than
   others. The models are trained with class weights so rare classes are not
   ignored, and judged on macro-F1 rather than accuracy alone.
3. **No dataset has triage urgency levels.** See "silver labels" in section 7.

### Arabic

The models are English-only. Arabic input is translated before the models see
it, by an **offline dictionary** of 310 symptom words and phrases
(`data/ar_en_dictionary.json`), longest phrase first, with Egyptian
colloquial forms included ("مش قادر اتنفس" → "cannot breathe"). It also
handles attached prefixes ("والصداع" → "headache") and Arabic word order
("ألم في الركبة" → "knee pain"). The red-flag rules additionally check the
original Arabic text directly.

## 6. Model 1 — which specialty?

| | |
|---|---|
| Input | The symptom text (after translation) |
| Output | One of 17 specialties, with a probability for each |
| Algorithm | TF-IDF + logistic regression (scikit-learn) |
| Size | 4,226 word features · 0.5 MB file |
| Training time | A few seconds on a laptop |
| Code | `src/train_specialty.py` — about 20 lines of actual modelling |

```python
Pipeline([
    ("tfidf", TfidfVectorizer(stop_words="english", ngram_range=(1, 2), min_df=2, sublinear_tf=True)),
    ("clf",   LogisticRegression(C=10, max_iter=1000, class_weight="balanced")),
])
```

What the settings mean, in case you are asked:

- `ngram_range=(1, 2)` — use single words and pairs of words.
- `min_df=2` — ignore words that appear in only one example (typos, noise).
- `stop_words="english"` — drop filler words.
- `class_weight="balanced"` — give rare specialties a proportionally louder
  voice during training.

**When the model is not trusted.** The model learned from full descriptions.
Two situations fall outside that, and the service handles them explicitly:

- **Low confidence** (best probability below 0.30): the keyword rules decide
  instead; if no keyword matches, the answer is "internal medicine".
- **Short input** (8 words or fewer, and fewer than 3 symptoms): the keyword
  rules are asked *first*. On one- or two-word inputs like "headache" the
  model alone is right only 55.6% of the time, the keyword rules 77.8%, and
  the combination 88.9% — so combining them is a measured decision, not a
  guess.

The `reasons` field always says which path was taken.

## 7. Model 2 — how urgent?

| | |
|---|---|
| Input | 159 numbers computed from the request |
| Output | LOW / MODERATE / HIGH / CRITICAL, with a probability for each |
| Algorithm | Random forest, 300 trees (scikit-learn) |
| Size | about 12 MB file |
| Code | `src/features.py` (the inputs), `src/train_risk.py` (training) |

### The 159 features

| Group | Features | Where they come from |
|---|---|---|
| Recognised symptoms (131) | one yes/no flag per known symptom | phrase matching against the symptom vocabulary |
| Severity weights (4) | number of matched symptoms; sum, maximum and mean of their weights | the 1–7 severity weights published with the dataset |
| Patient's own words (3) | severity level (mild / moderate / severe); duration in days; whether a duration was given | parsed from the text ("2 hours", "a week") |
| Patient profile (4) | age; whether age is known; vulnerable age (≤ 5 or ≥ 65); has a chronic disease | sent by NestJS from the patient profile |
| Body system (17) | the specialty model's probability for each specialty | model 1's output feeds model 2 |

The last group is why there are *two* models in a chain: which body system is
involved is a strong hint about urgency (a cardiac picture is more worrying
than a skin one).

### Where the labels come from — "silver labels"

To train a classifier you need the right answer for each example. No public
dataset says "this symptom description is HIGH risk". So the labels are
**derived**, and you must say so:

1. Each disease has an urgency level in the disease table (section 5).
2. The datasets do not contain what our app knows about a patient — reported
   severity, duration, chronic diseases (and age, outside DDXPlus). So for
   each training row we **simulate** several patients with random values for
   those.
3. A small function combines the two: start from the disease's urgency;
   "severe" raises it to at least HIGH; vulnerable age, chronic illness, or
   symptoms lasting two weeks raise it to at least MODERATE.

Labels produced this way are called **silver labels** (as opposed to *gold*
labels assigned by experts). This gives 8,670 simulated training requests.

The important subtlety: **the model never sees the disease name.** It must
recover the urgency from the symptoms and context alone — which is exactly
what it gets in production. So the risk metrics measure *how well the model
recovers our labelling scheme from symptoms*, not agreement with real triage
nurses. Say this sentence in the defence before someone asks.

### When the risk model is not trusted

| Situation | What happens | Why |
|---|---|---|
| It recognises none of the words | No opinion; the rule floors decide (LOW by default) | Otherwise it would answer from prior statistics alone |
| Short input (as defined above) | MODERATE at most | Trained on full descriptions; left alone it called "acne" HIGH |
| Full description | Any level, including CRITICAL | This is what it was trained and tested on |

## 8. The safety layer and the decision rules

Medical software wraps machine learning in explicit rules. Ours are the same
rules as the TypeScript engine in the back-end, ported to Python, and an
automated test fails if the two lists ever differ.

**Red flags** (`data/red_flags.json`) — 9 emergency categories, 57 phrases in
English and Arabic:

chest pain · difficulty breathing · severe bleeding · loss of consciousness ·
possible stroke · seizure · coughing blood · severe allergic reaction ·
suicidal thoughts

Any match → CRITICAL, emergency advice, SOS card. Checked on the original text
and on its translation. Simple substring matching on purpose: for an emergency
rule, triggering too often is the safe direction.

**Rule floors** — minimum levels the models cannot go below:

| Condition | Minimum level |
|---|---|
| Patient describes a symptom as severe / unbearable / worst | HIGH |
| 3 or more symptoms entered | MODERATE |
| Age ≤ 5 or ≥ 65 | MODERATE |
| Chronic disease on the profile | MODERATE |

**The principle, in one sentence:** *the models can raise a level that the
rules set, never lower it.* A red flag always wins. An ML mistake can
therefore never remove an emergency.

**Can the model declare an emergency by itself?** Yes, when it is given a full
description and no red-flag phrase matched. The original plan was "only rules
may declare an emergency". We measured what that missed — heart-attack and
brain-hemorrhage descriptions worded without any red-flag phrase, e.g.
"vomiting, breathlessness, sweating" — and switched it on. It is one constant
(`ML_MAY_DECLARE_EMERGENCY` in `src/engine.py`), and the report shows both
settings side by side. This is a good story for the defence: a design decision
changed by evidence.

## 9. Results, and how to read them

Everything here is measured on test data the models never saw during
training. Full tables and charts: `smartcare-ml/reports/metrics.md`.

### Specialty routing

| | Keyword rules (baseline) | Trained model | Full service |
|---|---|---|---|
| Accuracy on 786 held-out rows | 31.0% | **99.6%** | 99.6% |
| Macro-F1 | 0.192 | **0.992** | 0.992 |
| Only rows whose specialty the rules *can* answer (587) | 41.6% | 99.7% | |

By dataset — this breakdown matters:

| Test rows from | Rows | Rules | Model |
|---|---|---|---|
| Symptom2Disease (real patient wording) | 231 | 35.5% | **99.1%** |
| Disease Symptom Prediction (checklists) | 61 | 45.9% | 100% |
| DDXPlus (synthetic) | 494 | 27.1% | 99.8% |

**How to present it.** Quote 99.1% on Symptom2Disease as the honest number —
it is the dataset written in patients' own words. The DDXPlus figure is
flattering: those rows are assembled from a fixed list of phrases, so test
rows share their wording with training rows.

### Short inputs — how patients actually type

63 hand-written one- or two-symptom inputs in English and Arabic
(`data/short_inputs.csv`):

| | Keyword rules | Model alone | Full service |
|---|---|---|---|
| Acceptable specialty | 77.8% | 55.6% | **88.9%** |

This set is small and was used to design the short-input behaviour, so it is
a development number, not a blind test.

### The stress test — diseases the model has never seen

The normal test set contains *new descriptions of diseases that were in
training*. The harder question: remove a disease from training completely,
retrain, and ask where its patients should go. Repeated for 79 diseases:

**49.5% correct.**

Hepatitis A is still routed to gastroenterology when removed (the other
hepatitis types teach the pattern). Migraine is not routed to neurology when
removed (nothing else in training looks like it). Adding DDXPlus did not
improve this for the original diseases (47.8% without it, 46.4% with it, on
the same rows).

**How to present it.** "The model recognises the conditions it was trained on
very well and generalises to new conditions about half the time; that is why
the keyword rules and the internal-medicine default remain as a safety net,
and why more diseases per specialty is our main future work."

### Urgency

2,169 simulated requests built from the test rows (silver labels):

| | Keyword rules | Risk model alone | Full service |
|---|---|---|---|
| Accuracy | 46.8% | 89.8% | 69.7% |
| **Urgent recall** — truly HIGH/CRITICAL flagged as such | 68.0% | 91.5% | **93.6%** |
| Over-triage — non-urgent flagged urgent | 25.0% | 5.7% | 27.5% |

**Why is the full service's accuracy lower than the model's?** Because the
red-flag rules are deliberately over-cautious: any mention of chest pain or
shortness of breath becomes CRITICAL, even for conditions labelled HIGH or
MODERATE. That costs accuracy and buys safety — the full service has the
highest urgent recall. It is the same over-caution the back-end rules engine
already had.

### Emergencies

Of the 2,169 test requests, 208 are truly life-threatening (CRITICAL):

| | Rules alone | Rules + model |
|---|---|---|
| Reported as CRITICAL | 175 | **204** |
| Emergencies raised by the model alone | — | 29 |
| …of which false | — | 0 |

The 29 cases the model added are the argument for letting it declare
emergencies. Four truly critical cases are still not reported as CRITICAL.

### An experiment that did not win

The plan's stretch goal was to replace TF-IDF with **sentence embeddings**: a
pretrained neural network (`paraphrase-multilingual-MiniLM-L12-v2`) that turns
a whole sentence, in any of 50+ languages, into 384 numbers that capture its
meaning. In theory that should help with Arabic and with wording the model
has not seen. We kept the same classifier and the same data and compared
(`reports/embeddings_experiment.md`):

| Specialty model alone | TF-IDF (what we use) | Sentence embeddings |
|---|---|---|
| Held-out test rows | **99.6%** | 97.7% |
| …real patient wording (Symptom2Disease) | **99.1%** | 95.2% |
| Never-seen diseases | **49.5%** | 44.1% |
| Short English inputs | 57.5% | 57.5% |
| Short Arabic inputs (16 rows) | **50.0%** (via our dictionary) | 25.0% (raw Arabic) |

It was not better on any measure, and it would cost a ~470 MB model plus
PyTorch on the server and the loss of the per-word explanations. So the
service keeps TF-IDF. This is a useful result to present: the simpler,
explainable model was chosen by measurement, not by default.

## 10. Limitations — say these yourself

Stating limitations before the committee does is the strongest position.

1. **Not validated with real patients or clinicians.** All evaluation is on
   public datasets.
2. **Mostly synthetic data.** Two of the three datasets are generated, not
   collected from patients. High accuracy on them shows the method works, not
   that it works on real Egyptian patients.
3. **Urgency labels are derived (silver).** The risk numbers measure agreement
   with our own labelling scheme.
4. **The disease table is reference-reviewed, not clinician-approved.**
5. **Unseen diseases: about 50%.** Only 83 diseases are covered; specialties
   with no training disease (ophthalmology, for example) are reached only by
   keyword rules.
6. **Arabic is a dictionary.** Words missing from the 310 entries are
   invisible to the models. Red-flag phrases are still matched on the raw
   Arabic.
7. **Over-triage is high by design** (27.5%): the system prefers a false
   alarm to a missed emergency.
8. **Short inputs get rule-based answers.** One or two words are routed by
   keywords, and the risk model is capped at MODERATE for them.

What would fix them, in order of value: a clinician review of the disease
table; real, de-identified triage records from a partner hospital; more
diseases per specialty; a proper Arabic model.

## 11. Design decisions and their reasons

| Decision | Reason |
|---|---|
| Small classical models instead of an LLM (ChatGPT-style) | Zero running cost; patient text never leaves our server; every answer is explainable; no hallucination — the output is always one of a fixed list of labels. |
| A separate Python service instead of ML inside NestJS | scikit-learn is a Python library. A tiny HTTP service with one endpoint keeps the back-end untouched and the two parts independently deployable. |
| Strategy pattern + fallback in NestJS | The AI can be switched on, off, or replaced by configuration; an AI outage can never break triage. |
| Rules wrap the models | Emergencies must not depend on statistics. Rules are auditable line by line. |
| TF-IDF + logistic regression for specialty | The simplest model that works on text, and its weights are readable. A neural sentence-embedding model was tested and scored lower. |
| Random forest for risk | Works well on mixed tabular features without tuning. |
| Two models chained | Body system (model 1's output) is a strong signal for urgency (model 2). |
| Predict specialty and urgency, never a disease | Keeps the system assistive, not diagnostic. |
| Models committed to git | The server never trains; deploying is copying files and installing five packages. |
| Evaluation regenerated by one command | Numbers in the report cannot drift from the code. |

## 12. Questions the committee may ask

**"Is this a diagnostic system?"**
No. It never outputs a disease. It suggests a department and an urgency level,
shows its reasons, attaches a disclaimer, and stores the result for a doctor
to review.

**"Why didn't you use ChatGPT or another large language model?"**
Cost, privacy and explainability. An LLM API costs money per request and sends
patient text to a third party. Its answers cannot be traced to specific
inputs. Our models are free to run, stay on our server, and name the words
behind each answer. For a classification problem with a fixed set of answers,
a classical model is the right tool.

**"Why not deep learning?"**
With about 4,000 examples, a neural network would overfit and would not be
explainable. Logistic regression on TF-IDF already reaches 99% on held-out
data. We also tested the obvious deep-learning alternative — a pretrained
multilingual sentence-embedding model — and it did not do better (see "An
experiment that did not win" in section 9).

**"99.6% is suspiciously high. Is it real?"**
It is real for what it measures: new descriptions of diseases the model was
trained on, in datasets where each disease has a distinctive vocabulary. We
removed duplicates before splitting to avoid leakage, and we report two harder
numbers next to it: 99.1% on the real-wording dataset, and about 50% on
diseases removed from training entirely.

**"How do you know the urgency level is correct?"**
We do not have clinician-assigned urgency labels; nobody publishes them. The
labels are derived from a disease-level urgency table plus simulated patient
context. The metrics show the model recovers that scheme from symptoms alone.
Validating against real triage decisions is future work and needs a hospital
partner.

**"What if the model is wrong about an emergency?"**
Two directions. If it *misses* one: the red-flag rules run first and do not
depend on the model, and rule floors raise severe or vulnerable cases. If it
*raises a false one*: the patient is told to seek emergency care
unnecessarily — the safer error. On the test set the model raised 29
emergencies beyond the rules, none of them false.

**"What happens if the AI service crashes?"**
NestJS waits at most 8 seconds, then answers from the built-in rules engine
and marks the response `rules-fallback`. The patient still gets an answer.
(This can be shown live — section 13.)

**"How is patient privacy protected?"**
Only clinical context is sent to the ML service — no identifiers. The service
is bound to localhost and never exposed to the internet. Nothing is sent to
any third party. The ML service stores nothing.

**"Does it support Arabic?"**
Yes, through an offline dictionary that translates symptom words before the
models run, plus Arabic red-flag phrases matched directly. It is a dictionary,
not a language model, so uncommon wording can be missed — a stated limitation.

**"How would you improve it?"**
Clinician review of the disease table; real triage data; more diseases per
specialty; a multilingual text model for Arabic; monitoring of the doctor's
final assessment against the AI's initial one, which the database already
stores.

**"Why is the model allowed to declare an emergency? Isn't that risky?"**
We started with rules only and measured it: the rules missed 33 of 208 truly
critical test cases because the wording had no red-flag phrase. Letting the
model add emergencies recovered 29 of them with no false alarm. It can only
add emergencies, never remove one, and only on a full description.

**"What is the difference between your model and the rules engine you already
had?"**
The rules are a fixed list of keywords someone wrote. The model learned
weights for 4,226 words and word pairs from about 3,000 examples. On the same test data the rules route
31% correctly and the model 99.6%. The rules are still there — as the safety
layer, as the fallback, and for short inputs where they are more reliable.

## 13. Live demo script

```bash
cd smartcare-ml && .venv\Scripts\python -m uvicorn src.service:app --port 8000
npm run start:dev          # with AI_SERVICE_URL=http://localhost:8000 in .env
```

Open Swagger (`/docs`), log in as a patient, and call `POST /api/v1/ai/triage`.

| # | Send | Point out |
|---|---|---|

## 14. What was used

| Layer | Technology | Role |
|---|---|---|
| Language | Python 3.12 | ML service and training scripts |
| Machine learning | scikit-learn 1.9 | TF-IDF, logistic regression, random forest, metrics |
| Model files | joblib | Saving and loading the trained models |
| Web service | FastAPI + Uvicorn | `POST /triage`, `GET /health`, automatic OpenAPI docs |
| Validation | Pydantic | Request and response schemas matching the NestJS contract |
| Data work | pandas, NumPy | Cleaning, splitting, feature tables (training only) |
| Charts | matplotlib | Confusion matrices and feature-importance plots |
| Tests | pytest | 92 golden tests, including every red-flag phrase |
| Exploration | Jupyter notebook | `notebooks/01_explore.ipynb` |
| Integration | NestJS `MlHttpAiProvider` | HTTP client with 8-second timeout and rules fallback |
| Process manager | PM2 | Keeps the service running on the VPS |

The server needs only five Python packages (`requirements.txt`). pandas,
matplotlib and Jupyter are used for training and reports, not at runtime.

### Deployment

One command on the server, `npm run deploy:ml`, creates a Python virtual
environment, installs the five packages, runs a smoke test (the committed
models load and give the expected answers) and starts the service under PM2
next to the API. Then `AI_SERVICE_URL=http://localhost:8000` in the API's
`.env` switches it on. Nothing is trained on the server. The service uses
about 280 MB of RAM. The steps are in `docs/DEPLOYMENT.md` (section 6) and
were rehearsed on a clean Ubuntu 24.04 machine before the real deployment.

## 16. Glossary

| Term | Meaning |
|---|---|
| **Model** | A function learned from examples; here, a file loaded by the service. |
| **Training** | Running the learning algorithm on examples to produce the model. Done offline. |
| **Inference / prediction** | Using the trained model on a new input. All the server does. |
| **Classifier** | A model whose output is one label from a fixed list. |
| **Label** | The correct answer attached to a training example. |
| **Feature** | One number describing the input. Models only see features. |
| **TF-IDF** | A way to turn text into numbers: a word scores high if it is frequent in this text and rare in general. |
| **n-gram** | A sequence of n adjacent words; we use 1 and 2 ("chest", "chest pain"). |
| **Logistic regression** | A classifier that learns one weight per feature per class; readable. |
| **Decision tree** | A flowchart of yes/no questions on the features. |
| **Random forest** | Many decision trees that vote. |
| **Confidence** | The probability the model assigns to its chosen label. |
| **Train/test split** | Holding back part of the data (20%) to measure the model on examples it never saw. |
| **Stratified split** | A split that keeps each class in the same proportion on both sides. |
| **Cross-validation** | Repeating the split several times (5 here) to check the result is stable. |
| **Overfitting** | Memorising the training examples instead of learning the pattern. |
| **Data leakage** | Test information reaching training, inflating the score. |
| **Accuracy / precision / recall / F1** | See the table in section 4. |
| **Macro-F1** | F1 averaged over classes, each class counting equally. |
| **Confusion matrix** | Table of true class against predicted class. |
| **Baseline** | The simple method you compare against; here the keyword rules. |
| **Class imbalance** | Some classes having far more examples than others. |
| **Silver labels** | Labels derived by a rule or a table rather than assigned by experts (gold). |
| **Synthetic data** | Data generated by a program rather than collected from real people. |
| **Red flag** | A symptom phrase that by itself warrants emergency care. |
| **Rule floor** | A minimum risk level set by a rule; the models cannot go below it. |
| **Over-triage** | Telling a non-urgent patient that it is urgent. The safer error. |
| **Under-triage** | Telling an urgent patient that it is not urgent. The dangerous error. |
| **Acuity** | How urgent a condition is. |
| **ICD-10** | The WHO's international classification of diseases; each disease has a code. |
| **Explainability** | Being able to say why the model gave an answer. |
| **Strategy pattern** | A design pattern: one interface, interchangeable implementations chosen at runtime. |
